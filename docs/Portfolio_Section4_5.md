## 배운 점

### 1. 클라이언트 개발자도 서버 구조를 알아야 한다

서버가 데이터를 어떻게 계산하고 어떤 형태로 내려주는지 이해하지 못하면, 클라이언트 설계에서 잘못된 가정을 하게 된다. 직접 양쪽을 만들면서 "클라이언트가 무엇을 믿어야 하고 무엇을 직접 처리해야 하는가"를 구체적으로 체감했다.

### 2. 데이터 흐름을 정의하면 코드가 단순해진다

서버 응답 → 캐시 갱신 → 이벤트 → UI라는 단방향 흐름을 원칙으로 정하고 나니, 각 레이어가 독립적으로 동작해 디버깅과 기능 추가가 쉬워졌다. 설계 원칙 하나가 코드 전체의 복잡도를 낮춘다는 것을 실감했다.

### 3. 환경 설정 문제는 기능 문제와 다르게 접근해야 한다

기능 버그는 로직을 따라가면 원인을 찾을 수 있지만, 환경 설정 문제는 어느 레이어에서 깨졌는지부터 범위를 좁혀야 한다. 배포 환경을 직접 구축하면서 "지금 문제가 코드인가, 환경인가"를 먼저 분리하는 습관이 생겼다.

### 4. 전체를 보는 개발자가 되고 싶다는 방향이 생겼다

1인 개발로 전체 스택을 경험한 덕분에, 클라이언트 코드 한 줄이 서버·DB·배포 어느 지점과 연결되는지 구조적으로 파악하는 시각이 생겼다. 팀 개발 환경에서 클라이언트 포지션으로 일하더라도, 서버·인프라 팀과 구체적으로 소통할 수 있다는 자신감을 얻었다.
